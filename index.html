Why a fixed rule gets this wrong

Same endpoint, same payload, same policy

A static rule has one answer for POST /v2/ledger/entries/:id/reverse. Either contractors may reverse a ledger entry or they may not — and whichever you pick is wrong roughly half the time. Where it sits

Code analyzer

Scans the repository and rates each finding by how reachable it actually is, not by rule severity alone. A SQL concatenation on a route the support-agent role can reach is rated above the same pattern behind an admin guard. Every finding carries a suggested patch and the commit that introduced it.

API guardrail
in-line · pre-service

Inspects the request before it reaches the service, scores it, and returns a decision. Blocked calls never touch the upstream. Flagged calls complete and raise a review event, so a false positive costs a triage item rather than an outage.

03

How a decision is reached

Median in-line cost: 12–21ms on stopped calls
1
Resolve the context

Identity, role, session age, device recognition, tenant claim, environment and the caller’s own baseline are assembled into one evaluation object. No network calls — the baseline is kept warm per identity.

actor · session · object · rate · env
2
Classify the payload

Bodies are scanned for PII classes, executable fragments and entropy that does not match prior values for that field. Classification results become context fields the policies can match on.

payload.classification · payload.matches · payload.entropy
3
Evaluate matching policies

Only policies whose path and method selectors match are evaluated. Each condition that holds contributes a weight; some weights are negative, so a fresh step-up assertion or an established service identity actively lowers the score.

weights are signed · negative evidence counts
4
Apply thresholds

Below 45 the request is forwarded. Between 45 and 70 it completes and raises a review event. At 70 and above the guardrail rejects it with 403 before the service is reached.

allow < 45 · flag 45–69 · block ≥ 70
5
Record the reasoning

Every decision is written with its factor breakdown, the policy that produced it and the request id. You can reconstruct why any call was stopped months later, which is the part that matters when someone asks.

append-only · 30-day request retention · exportable
04

Policies are versioned text

Reviewed in the repository, tested before merge

A policy is a selector, a condition set and an action. Conditions reference context fields rather than literals wherever the literal would age badly — the export threshold below is a deviation from the caller’s own baseline, not a row count somebody picked in 2023.

policies/POL-022.yaml owner: analytics 
id:       POL-022
name:     "Throttle bulk export by role"
action:   flag           # allow through, raise a review event
severity: medium

select:
  path:   /v2/exports/*
  method: [GET, POST]

when:
  # Deviation from this identity's own 30-day baseline —
  # not a fixed ceiling that is wrong for every team at once.
  - rate.zscore       >  3.0
  - actor.role        not_in [service-account]

weights:
  rate.zscore:        30
  result.rows:        20
  actor.role:         13
  actor.is_baselined: -10   # established pattern lowers the score

The console ships a test bench that runs this evaluator against a request context you can edit, and prints a per-condition trace. You can see which condition failed before the policy reaches production traffic.
